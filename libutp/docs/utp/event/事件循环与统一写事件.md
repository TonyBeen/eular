# 事件循环与统一写事件

## 1. 所有权

Context 借用调用方提供的 libevent `event_base`，注册一个 UDP 可读事件、一个统一 UDP 可写事件、一个协议定时器事件和一个 Stream 零延迟通知事件。Context 不创建或驱动 event base。

## 2. 收包

可读事件从 UDP socket 收包；Linux 优先使用 `recvmmsg`，其他平台使用单包接收。Context 取得 PacketIn 对象、记录 peer/local endpoint，然后按 NAT_PROBE、RENDEZVOUS、Connection CID 和 pending CID 顺序分流。解析错误按包类型和连接状态处理，不能让未知 UDP 数据创建 Connection。

## 3. 发包

所有 Connection 共用 Context 的 writable 事件。发送遇到 `UTP_STATUS_WOULD_BLOCK` 时，PacketOut 回到发送控制队列并开启该事件；事件恢复后继续刷新各连接队列。帧或功能模块不得各自注册独立写事件。

普通连接、Rendezvous Initial、ACK、重传、PATH 验证和 MTU 探测都经过同一发送入口；MTU 探测包在发送错误处理上单独消费 `EMSGSIZE`，但不绕过统一 writable 机制。

## 4. 定时器

统一定时器选择最早截止时间，驱动 ACK 延迟、PTO/重传、握手重试、保活、NAT 阶段、NTRS 控制重试、路径验证和 MTU 探测。定时器回调只推进状态和排队数据，实际 UDP 写入仍由 writable 事件执行。

## 5. Stream 通知

Stream 的可读、可写回调不复用协议定时器。Context 使用独立的零延迟 one-shot timer，分别维护可读和可写队列；回调派发前转移当前队列快照，回调中重新满足条件的 Stream 留给下一轮事件循环。这样保持水平触发，同时不会在一个 timer 回调内反复派发未消费的 Stream。

## 6. 致命错误

`WOULD_BLOCK` 是可恢复的发送时机；内存不足、socket 致命错误、事件注册失败或协议状态错误按调用层约定记录并收敛。Context 不在底层静默吞掉非 WOULD_BLOCK 的发送错误。
