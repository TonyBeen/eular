# libutp 测试计划

> 更新时间：2026-09-15
> 当前主测试体系位于 `utp/test`，由 CMake/CTest 管理；根目录旧的 C++ `utp_tests` 仅作为历史兼容目标，不是 C11 测试入口。

## 1. 构建和日常回归

```sh
cmake -S utp -B build-c -DUTP_C_BUILD_TESTS=ON -DUTP_C_BUILD_EXAMPLES=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-c --parallel
ctest --test-dir build-c --output-on-failure
```

当前 C11 测试目标包括 `utp_c_api_test`、`utp_c_public_api_test` 以及 proto、crypto、packet_in/out、send_control、pending_incoming、stream、connection、congestion、MTU、NAT、parser 和 transport integration 等 `utp_c_*_test`。实际测试数量以 `ctest -N` 为准，不在文档中固定 assertions 数量。

NTRS 集成测试只有在 Linux 且提供已构建的 NTRS 可执行文件时启用：

```sh
cmake -S utp -B build-c-ntrs -DUTP_C_BUILD_TESTS=ON \
  -DUTP_C_NTRS_EXECUTABLE=/absolute/path/to/ntrs
cmake --build build-c-ntrs --parallel
ctest --test-dir build-c-ntrs --output-on-failure
```

## 2. 故障注入、Sanitizer 和 Fuzz

Linux 批量 socket 故障测试由 CMake 在检测到 `sendmmsg/recvmmsg` 时自动加入：

```sh
cmake -S utp -B build-fi -DUTP_C_BUILD_TESTS=ON
cmake --build build-fi --parallel
ctest --test-dir build-fi --output-on-failure
```

C11 sanitizer 构建：

```sh
cmake -S utp -B build-asan -DUTP_C_BUILD_TESTS=ON \
  -DUTP_C_ENABLE_SANITIZERS=ON -DUTP_C_SANITIZER_LIST=address,undefined
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure
```

Clang Fuzz 目标使用 `-DUTP_C_BUILD_FUZZERS=ON`，再运行 `cmake --build <dir> --target utp_c_fuzz_packet_parser`。Fuzz 入口是包/帧解析器，不依赖网络服务。

## 3. 协议回归重点

每次修改以下模块都应至少运行对应测试：

- Initial、Handshake、HandshakeDone、0-RTT 和 pending：`transport_integration`、`pending_incoming`、`connection`。
- ACK、PTO、丢包和重传：`send_control`、`send_ledger`、`receive_history`。
- Stream、FIN、RESET 和流控：`stream`、`connection`。
- PATH_CHALLENGE/PATH_RESPONSE、抗放大和 MTU：`connection`、`mtu`。
- NAT Binding、分类和两轮窗口：`nat`。
- Rendezvous 编解码及 NTRS 端到端：`proto`、`ntrs_integration`。

重点覆盖重复包、乱序、HandshakeDone 丢失、关闭帧、认证失败、路径变化、EMSGSIZE、WOULD_BLOCK、ENOBUFS 和资源分配失败。

## 4. 网络仿真和长稳

仓库当前没有 `test/scripts/netem_*.sh`，不能把它们当作可执行入口。Linux 上可使用 `tc netem` 对 echo example 或集成测试进程施加 delay、loss、reorder 和 rate，并记录吞吐、RTT、握手成功率、重传率、P99 尾延迟、RSS 和 fd 数。

发版前应补充：

- 1%/5% 丢包、50/200 ms 延迟、乱序和混合网络条件；
- 多连接、多流和短连接建立/关闭循环；
- 至少数小时的 ASan/UBSan 或 Valgrind 长稳运行；
- NTRS 注册、保活丢包、反注册、重复 REQUEST 和双向 Rendezvous。

## 5. 测试记录原则

记录源码提交、编译器/标准库、CMake 选项、测试命令和失败日志。协议或公共 API 改动不得只依赖手工抓包，应增加可重复的 C/C++11 测试用例。
