# libutp 写链路设计：内存流转与加密减拷贝分析

## 1. 概述

当前 C 实现使用 Stream ring buffer、PacketOut slice 和独立的加密输出缓冲，平衡应用层易用性、可靠重传和加密开销。文档中的类型和接口均对应 `utp/src/` 与 `utp/include/utp/`。

## 2. 数据流转模型

### 阶段 1：应用层到 Stream ring buffer

- 普通 `utp_stream_write()` 将数据复制到 `utp_stream_t` 的发送 ring buffer 中。
- 发送数据必须保留到 ACK 到达，以支持丢包重传和 MTU 变化后的重新切片。
- `utp_stream_acquire_write_views()` 可直接取得 ring buffer 的可写视图，应用通过 `utp_stream_commit_write_views()` 提交，从而跳过应用缓冲到 ring buffer 的复制。

### 阶段 2：ring buffer 到 PacketOut

- 发送控制器从 ring buffer 按流 offset 选择数据，写入 PacketOut 的 raw/slice 表示。
- 启用 AEAD 时，明文包经过加密后写入独立的加密输出缓冲。
- PacketOut 保留重传所需的包号、帧元数据、流 offset 和发送尝试链；重传使用新包号重新编码和加密。

### 阶段 3：PacketOut 到内核

- `utp_udp_socket_send()` 或批量发送接口将 PacketOut 交给 `sendmsg`/`sendmmsg`。
- 用户态到内核的复制属于标准 UDP socket 语义；`WOULD_BLOCK` 时保留 PacketOut，等待 Context 的统一 writable 事件。

## 3. 拷贝次数总结

| 阶段 | 当前 C 路径 | 说明 |
| :--- | :--- | :--- |
| 应用层 -> Stream 缓冲 | 0-1 次 | `acquire/commit` 为 0 次，普通 write 为 1 次 |
| Stream 缓冲 -> PacketOut | 0-1 次 | PacketOut slice 可直接引用缓冲；加密时写独立输出 |
| PacketOut -> 内核 | 1 次 | 由操作系统 UDP socket 完成 |

## 4. 关键设计约束

1. 每个包都有唯一 Packet Number；重传必须用新包号重新加密，不能直接复用旧密文。
2. Stream ring buffer 是业务数据的可靠副本，PacketOut 只保存当前发送尝试和必要的帧元数据。
3. PacketOut 的生命周期由发送控制和 ACK 共同管理；应用写入完成后可以立即复用输入缓冲区。
4. MTU 探测包单独构造，不应占用业务 Stream 的待发送片段，也不应因 `EMSGSIZE` 影响业务包。
5. 任何新增路径都必须明确数据的所有者、借用期限和释放时机，不得把临时应用指针放入重传队列。
