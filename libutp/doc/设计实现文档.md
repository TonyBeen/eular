## 3. 已实现功能

### 3.1 连接与事件模型

当前仓库已经落实以下连接能力：

- Context 提供 bind、connect、accept 等入口。
- 主动建连成功后可进入 Connected。
- 被动建连采用两阶段接入：先收到请求，再由应用显式 accept 放行。
- `utp_context_set_on_connected()`、`utp_context_set_on_connect_error()` 和 `utp_context_set_on_connection_error()` 已具备可用语义。
- OnNewConnection 可用于被动连接的准入决策。

当前实现特点：

- 被动连接不是“收到 Initial 就直接变成正式连接”，而是 pending -> accept -> 等待 HandshakeDone -> 晋升 Connected。
- 同步前置失败与异步握手失败都统一汇总到连接结果事件中。
- HandshakeDone 不再按“发送成功即收敛”处理，而是以 ACK 覆盖为准；超时会继续重发。
- pending 阶段对未携带 HandshakeDone 的后续包采用小窗口缓存，收到 HandshakeDone 后回放，降低尾部丢包连锁影响。

### 3.2 Stream 数据面

当前已落实：

- createStream / getStream
- 流收发缓冲
- read / write
- FIN / RESET_STREAM 基本语义
- 零拷贝 acquire / commit 接口
- 流 ID 准入与活跃流配额校验

说明：

- 当前流模型已经不是“只有帧编解码”，而是完整接入了连接主流程。
- 流关闭、可读、异常终止在 API 层已有对外语义。

### 3.3 Stream 优先级与调度

当前已落实：

- `utp_stream_set_priority()` / `utp_stream_priority()` 接口
- 默认优先级与优先级范围定义
- `utp_context_options_t.stream_scheduler_mode`
- STRICT 与 DRR 两种调度模式
- Connection 内的 Stream 调度统计字段

当前结论：

- stream 优先级能力已经落地，不再属于“只有设计没有实现”的阶段。
- 剩余工作主要是高负载收益验证、指标看板化和参数进一步调优。

### 3.4 包解析与发送对象生命周期

当前已落实：

- 固定头解析
- payload 长度校验
- 帧遍历
- PacketOut 池化管理
- PacketIn 池化接入主收包路径
- PacketOut attempt 链记录每次发送尝试

实现意义：

- 发送侧已经能保留“一个逻辑包多次发送尝试”的轻量历史。
- 接收与发送对象都已有可复用的内存生命周期管理。

### 3.5 ACK、丢包检测与重传

当前已落实：

- Ack 编解码
- ACK 范围解析
- ACK 驱动的 inflight/unacked 回收
- ACK timer
- 包阈值 ACK
- 乱序快速 ACK
- ACK piggyback
- FACK + 重排序阈值丢包检测
- 丢包队列管理
- 使用新包号的重传策略

当前结论：

- 发送恢复闭环已经形成，不再是单向 ACK 解码。
- AckFrequency 不只是帧定义，已经参与 ACK 策略与发送侧重排序阈值联动。

### 3.5.1 握手参数职责收敛

当前已落实：

- TransportParams 已从 Crypto 中拆出为独立帧
- 握手阶段 Initial 和 Handshake 都发送 TransportParams 与 AckFrequency
- `TransportParams.max_ack_delay` 已删除，ACK 最大延迟只保留在 AckFrequency
- 运行期发送侧超时计算改为采用对端 AckFrequency 宣告的 `max_ack_delay_ms`
- 主动侧 HandshakeDone 定时采用 `min(local_handshake_timeout, peer_handshake_timeout) / 3`

当前语义：

- Config 中的 `handshake_timeout` 同时是本端握手首轮超时基准，并通过 TransportParams 向对端声明建议值。
- 收到对端 `handshake_timeout` 后，握手相关定时采用 `min(local, peer)`；重试次数仍由本地配置控制。
- 连接建立后，ACK 行为主要采用对端发来的 AckFrequency；握手超时不由对端单方面放大。

### 3.5.2 协议 v3 握手辅助与确认语义（进行中）

已确认的设计目标：

- AckFrequency 删除 `timestamp` 字段，保留 `ack_eliciting_threshold/reordering_threshold/max_ack_delay_ms`
- 新增 HandshakeDelay 帧，字段 `delay_time_us`（4 字节，微秒）
- HandshakeDone 从 1 字节扩展为 9 字节：`type + ack_handshake_pn(8B)`

语义约束：

- Handshake 的 HandshakeDelay 表示“收到 Initial 到发出 Handshake”的处理耗时
- 携带 HandshakeDone 的包也必须携带 HandshakeDelay，表示“收到被确认 Handshake 到发出 HandshakeDone”的处理耗时
- HandshakeDone 指定确认的是哪一个 Handshake 包号，提升重传场景下的收敛精度

版本策略：

- 当前仓库直接使用协议 v3，不提供旧版本兼容门控；部署时需保证通信两端使用兼容的协议版本。

### 3.6 拥塞控制与速率控制

当前已落实：

- BbrV1 默认接入发送控制
- Cubic 已接入发送控制（可通过 `cc_algorithm=2` 切换）
- pacer 与发送窗口联合门控
- ACK 驱动带宽与 RTT 采样
- BBR/Cubic 均已支持关键参数配置化（init/min cwnd、增益与阈值）

当前仍未完成：

- BBR 尚有少量关键常量仍为内部固定值（例如 ProbeBW 增益循环、ProbeRTT BDP 倍率、类似 RTT 阈值）
- 拥塞控制专项回归覆盖仍需扩展（模式切换、恢复分支、长时曲线回归）

### 3.7 路径验证、迁移与抗放大

当前已落实：

- 地址变化检测
- PathChallenge / PathResponse
- Unknown / Validating / Validated / Failed 路径状态
- active_path / candidate_path 双路径模型
- validating 阶段的抗放大门禁

当前结论：

- 当前代码已经按“验证成功后再切换”的保守迁移模型工作。
- 候选路径失败不会直接拖垮当前业务路径。

### 3.8 Keepalive 与 MTU

当前已落实：

- Ping 空闲保活
- 收到任意包刷新活动时间
- 连续无响应超时断开
- MTU 梯队探测
- 二分收敛
- MTU 黑洞回退

这意味着当前实现已经具备基础在线路变化场景下的可持续运行能力，而不只是“理论预留”。

### 3.9 安全、票据与 0-RTT

当前已落实：

- X25519Wrapper
- 基于 SHA-256/HKDF 的 traffic key schedule
- client->server 与 server->client 方向隔离的 key/nonce prefix
- AesGcmContext
- TokenAuth
- Crypto 帧与握手主流程接入
- 包级 AES-GCM 加解密
- SessionToken 编解码与导出
- `utp_connect_0rtt_options_t`
- `utp_context_connect_0rtt()`
- 票据验签、有效期校验、peer 绑定校验
- 短窗口抗重放去重
- 全零 X25519 shared secret 拒绝
- 加密请求缺失 traffic keys 时 fail closed

当前接口层也已具备：

- `utp_connection_set_on_session_token_ready()`
- `utp_connection_export_session_token()`

安全边界：

- 当前 X25519 握手没有 Ed25519 身份签名，不能认证对端，不能抵御主动公钥替换型中间人攻击。
- 当前 HKDF transcript 绑定协议版本、双方 CID、双方临时公钥和算法类型，但尚未绑定 userId/deviceId/keyId、随机数和中心目录证明。
- 当前没有 Finished key confirmation，因此不能把现有 Crypto 帧等同于最终端到端身份握手。
- 0-RTT 早数据可能被重放，应用只能放入幂等或自行去重的数据；Context 会保留早期响应直到 HandshakeDone 确认或超时清理。

### 3.10 关闭收敛

当前已落实：

- 连接进入 CloseSent/CloseReceived 后停止普通数据面发送
- 再次收到 close 时可在有限次数内重发 close
- 等待若干 PTO 后统一收敛到 Disconnected

关闭行为已经从“收到 close 就立即析构”提升为“有界收尾”。

## 4. 待完善功能

以下能力不是完全没有基础，而是“已有部分实现，但还不够完整或还缺关键收尾”。

### 4.1 BBR 剩余关键常量配置化

现状：

- BBR 已支持 init/min cwnd、startup gain、cwnd gain、startup 增长阈值、startup 轮数、ProbeRTT 时长、min_rtt 过期时间
- 仍有部分常量采用内部固定值

缺口：

- ProbeBW 增益循环参数化（当前为固定数组）
- ProbeRTT 基于 BDP 的倍率参数化
- 类似 RTT 判定阈值参数化

### 4.2 BBR/Cubic 测试覆盖扩展

现状：

- 已有 BBR/Cubic 配置生效与基础行为测试
- 构建与基础回归可稳定通过

缺口：

- BBR 模式迁移（StartUp/Drain/ProbeBW/ProbeRTT）轨迹回归
- BBR 丢包恢复窗口与 app-limited 分支回归
- Cubic 在不同 RTT/丢包模式下的增长与收敛曲线回归
- BBR 与 Cubic 切换后的对比基准回归

### 4.3 连接级端到端回归

现状：

- 帧级和模块级单测已经较多
- 典型端到端闭环覆盖仍不充分

缺口：

- 主动/被动混合建连回归
- 握手后数据面收发回归（含 HandshakeDone 丢失与恢复路径）
- ACK、丢包、重传串联回归
- 路径迁移与抗放大联动回归

### 4.4 可观测性仍可继续补强

现状：

- stream 调度已有一组统计字段
- ACK 与 0-RTT 已有部分行为可观察

缺口：

- 0-RTT 接受/拒绝原因的统计化输出
- path validation 关键事件计数
- MTU 黑洞与恢复路径的统一指标

### 4.5 内部实现一致性

现状：

- 主连接收包路径已经使用 PacketIn 池
- pending 握手解码路径与主路径仍有实现差异

缺口：

- 统一 pending 路径和正式连接路径的对象复用方式
- 减少同一类逻辑在不同路径上的维护分叉

### 4.6 非池化内存分配优化

现状：

- 核心报文对象（PacketIn/PacketOut）已实现池化，极大降低了主路径抖动。
- 但在连接管理、控制平面及部分辅助路径上仍存在非池化、高频触发的堆分配。

缺口（优化目标）：

- **PacketOut 缓冲区**：`utp_packet_out_buffer_pool_t` 按固定大小分桶并惰性按组扩容；应继续验证高并发下各桶的峰值和回收水位。
- **连接和流槽位**：Context 的连接/pending 槽位和 Connection 的 Stream 状态由所属对象管理；仍需评估大量短连接、开流/关流时的扩容和回收开销。
- **ACK/控制状态**：发送控制和控制帧槽位已经是 Connection 内的固定数组或受限队列；需要补充极端控制帧堆积时的拒绝与恢复测试。
- **拥塞控制状态**：BBR/CUBIC 状态直接嵌入 Connection 的发送控制对象；应继续验证切换、重置和销毁时没有遗留动态状态。
- **加密上下文**：Crypto 上下文在握手期按连接创建并在销毁时清理；高并发建连场景需要单独测量分配峰值。
- **接口数据形态**：公共 API 使用指针 + 长度和显式 capacity；新增辅助接口不得重新引入隐式 NUL 或容器拷贝。

说明（pending 路径与正式路径的一致性收敛主要指什么）：

- 目前 pending 阶段（被动侧 accept 后、晋升 Connection 前）与正式连接阶段在收包解码、PacketIn 复用、ACK 触发时机、异常路径处理上仍有两套相似但不完全一致的实现。
- 一致性收敛的目标是：同类输入在两条路径上得到尽量一致的行为语义（解码结果、缓存策略、ACK/重传触发、错误码与统计输出）。
- 这项工作本质是“消除双轨实现分叉”，降低维护成本和回归风险，避免同一问题在 pending/正式路径上出现不一致修复。

## 5. 下一步计划

下一步建议按优先级推进，而不是平均用力。

### 5.1 P0

- 引入 Ed25519 设备身份、中心公钥目录校验、签名 transcript 与双向 Finished，Finished 成功前不得向应用报告安全会话可用
- 将中心信令、NAT 候选路径发现与端到端密钥协商分层，中心不得接触临时私钥、shared secret、派生密钥或明文
- 扩展被动建连与 HandshakeDone 收敛回归测试（覆盖乱序到达、重复重传和缓存回放）
- 补齐路径迁移成功/失败/忽略错误响应的行为测试
- 补齐 0-RTT 合法票据、过期票据、无效票据的回归测试
- 增加 0-RTT 接受/拒绝、路径验证结果的可观测统计

### 5.2 P1

- 完善连接级端到端测试场景
- 将 attempt 链统计进一步接入 RTT/重传分析
- 统一 pending 握手路径与主收包路径的池化实现
- 补充多连接发送公平性测试，但当前没有独立的连接级 WDRR 配置或算法承诺
- 记录并推进 BBR 剩余关键常量的配置化收口

### 5.3 P2

- 扩展 BBR/Cubic 拥塞控制专项回归覆盖
- 继续扩展压力测试和长连接回归
- 整理并降低现有工程告警噪声

### 5.4 数据拷贝路径优化清单（后续执行）

以下清单用于指导后续“减少无效拷贝、降低 CPU 与内存带宽开销”的专项优化。

P0（优先落地）：

- 发送路径：减少 Stream 发送缓冲区到组包载荷之间的重复拷贝次数，优先评估 `utp_packet_out_slice_t` 的批量视图拼装与分片直写可行性。
- 接收路径：继续评估 Stream 乱序分片重组中的中间复制，保持 PacketIn 引用和流控语义不变。
- 加密路径：梳理 `raw_data/encrypt_data` 双缓冲策略，在不影响重传与调试语义的前提下，评估 in-place AEAD 或延迟分配（Encrypt-and-Copy）策略。注意每次重传需分配新 Packet Number 并作为 AAD 参与加密，延迟分配在最终发包前加密更具可行性。

P1（次优先级）：

- 应用读写路径：推广 `acquire/commit` 零拷贝接口使用，减少 `write/read` 传统接口在热点场景下的 memcpy。
- Stream 发送缓冲扩容：围绕 `utp_stream_t` 的发送 ring buffer 评估分级扩容和减少搬迁频次。
- 帧编解码：评估 STREAM 载荷从“拷贝编码”向 `utp_packet_out_slice_t`/`iovec` 分片发送演进的边界条件与兼容方案。

P2（长期优化）：

- 内核发送路径：在平台允许时评估批量发送 (`sendmmsg`)、`sendmsg + iovec` 以及 GSO（Generic Segmentation Offload）等能力，降低用户态拼包及系统调用拷贝成本。
- 内核接收路径：评估批量收包 (`recvmmsg`)、GRO（Generic Receive Offload）与缓冲复用策略，减少每包动态分配、复制及内核上下文切换开销。
- 异步 I/O 终极演进：评估在 Linux 5.1+ 环境下引入 `io_uring` 替代传统 `libevent` 事件循环，并结合 Fixed Buffers（预注册物理页）实现真正的跨内核边界零拷贝。

验收与约束：

- 逐项优化必须保持现有语义不变：重传、乱序重组、ACK 驱动恢复、加密完整性校验不回退。
- 每项优化需配套微基准与回归：吞吐、P99 时延、CPU 占用、拷贝字节数四项至少覆盖两项。
- 优化默认优先在实现层完成，不改协议线格式；若涉及协议变更，需单独评审。

## 9. 连接级调度边界

当前实现只承诺 Connection 内的 Stream Strict/DRR 调度，不承诺连接级 WDRR。若未来增加连接级调度，应单独增加公共配置、统计和测试，并在本节更新，不应把设计草案写成当前能力。

### 9.1 当前约束

1. Context 统一驱动所有 Connection 的写事件。
2. 每个 Connection 内部先按 Stream 调度，再受 cwnd、pacer、流控和路径限制。
3. 文档不描述代码中不存在的连接级量子、deficit 或 WDRR 开关。

### 9.2 未来评审要求

1. 若实现连接级公平，必须先新增明确的公共配置和统计字段。
2. 必须覆盖多连接、不同包长、丢包和高 RTT 回归。
3. 不得改变帧格式、ACK、重传和拥塞控制语义。

### 9.3 当前实现关系

Stream 调度只在 Connection 内执行；Context 的统一 writable 事件负责重试所有 Connection 的待发送包，不新增每种帧的独立写事件。
