# libutp 功能实现细节

> 本文档记录当前 `c/` 实现的功能职责、状态和关键实现细节。
> 协议字段、帧格式和线上兼容规则以 `docs/superpowers/` 下的协议文档为准；
> 本文不把旧版 `cpp/` 作为运行时依赖或行为基线。

## 1. 文档边界与权威顺序

1. `docs/superpowers/`：协议需求、线格式和设计决策。

## 2. Context 与连接生命周期

### 2.1 Context

`utp_context_t` 负责一个 UDP 端口上的所有连接和协议级任务：

- 持有一个 UDP socket、读事件、统一写事件和协议定时器。
- 按本地 CID 索引活动连接；按 `attempt_id`、打洞 token 和 pending CID 维护握手期索引。
- 预分配连接槽位、pending 槽位和入站 PacketIn 对象；发送缓冲由 Context 级 PacketOut 池共享。
- 维护 NAT 探测、NTRS 注册、地址样本聚合、Rendezvous 转发缓存和 0-RTT 重放表。
- 所有协议定时器由 Context 的统一定时器驱动，连接只保存截止时间和待处理状态。

Context 创建时复制 `peer_id`，并初始化本地传输参数、ACK 策略、拥塞控制、MTU 和保活默认配置。销毁 Context 不隐式向 NTRS 反注册；需要反注册时调用对应的公开 API。

### 2.2 连接与 CID

- 主动连接和被动连接都由 Context 分配本地 CID。
- CID 为非零随机值；发生碰撞时只进行有限次重新生成，超过次数返回连接 CID 冲突错误。
- 活动连接按 CID 解复用。握手阶段还按 `attempt_id` 归并同一次连接尝试，连接建立后主要使用 DCID/SCID 处理报文。
- `attempt_id` 只用于本次握手尝试及短期迟到报文去重，不作为已建立连接的数据面主键。
- 直连和 NTRS 协调都使用同一套握手路径；Rendezvous 只提供候选 endpoint 和开洞反馈，不改变 UTP 连接状态机。

### 2.3 主动握手

1. `utp_context_connect()` 分配本地 CID 和 `attempt_id`，保存目标 peer ID 与候选地址。
2. 写事件发送 Initial；UDP 暂不可写时保留待发送包，由统一 writable 事件重试。
3. 收到合法 Handshake 后进入 Connected，并排队 HandshakeDone。
4. HandshakeDone 以 ACK 覆盖作为收敛条件；丢失时由定时器重传，不要求应用再次发起连接。
5. 超过本地握手重试预算后，连接以超时错误结束，并通过连接错误回调通知应用。

### 2.4 被动握手

- 收到 Initial 后先建立 bounded pending 状态，不立即暴露为正式 Connection。
- 应用通过 `on_new_connection` 回调决定是否接受；接受后发送 Handshake，并等待匹配的 HandshakeDone。
- HandshakeDone 到达前的少量后续包进入有界缓存；晋升成功后按原顺序回放。
- pending 超时或重试耗尽时回收槽位，不产生已建立连接回调。
- 相同 `attempt_id` 的重复 Initial 复用已有 pending 状态；不覆盖已经确认的 CID、密钥或握手参数。

### 2.5 关闭与异常

- 本地主动关闭进入 CloseSent，停止普通数据发送，排队 ConnectionClose。
- 收到对端关闭进入 CloseReceived，并在有限窗口内回发关闭帧。
- Close/PTO 收尾完成后进入 Disconnected，再从 Context 连接表移除。
- 建连前失败触发连接错误回调；已建立连接后的异常触发连接关闭回调。每个结果只通知一次。
- `WOULD_BLOCK` 只表示当前写机会不足，由统一写事件重试；其他系统错误按公共错误码向上报告。

## 3. Packet、Frame 与发送控制

### 3.1 入站路径

`utp_packet_in_t` 从 Context 的 PacketIn 池取得。入站路径依次完成：

1. UDP 地址和长度检查。
2. 固定包头解析、版本和 payload 长度校验。
3. 帧游标遍历和帧类型位图构造。
4. 按包类型分派到 NAT、Rendezvous、pending 或 Connection。

解析过程不为包内容分配内存；所有帧都引用当前 PacketIn 的受控存储。格式错误包被丢弃并保留已有连接状态。

### 3.2 出站路径

- PacketOut 由 Context 级缓冲池按 1280、1500、4096、9000 和 65535 等大小档位惰性扩容。
- 申请一次通常批量获取一组对象，池耗尽时才申请下一组；正常 established 路径不因每个包单独申请结构体而抖动。
- PacketOut 保存包号、目的 endpoint、帧元数据和发送尝试信息，支持 ACK 回收和新包号重传。
- 所有模块把待发送对象放入本地队列；写失败为 `WOULD_BLOCK` 时保留对象并等待统一 writable 事件，不由每个功能重复注册写事件。
- 发送路径先处理关闭、握手、ACK、重传和路径控制，再按流调度选择业务数据。

### 3.3 ACK、丢包和重传

- 接收侧按 AckFrequency 记录 ack-eliciting 包、乱序和延迟 ACK。
- 发送侧保存未确认 PacketOut，收到 ACK 后更新 RTT、拥塞控制和在途字节统计。
- 快速丢包检测使用包号重排序阈值；定时器负责 PTO 和超时重传。
- 重传重新分配包号并重新构造/加密报文，不复用旧包号。
- 重传对象和 ACK 状态由 Connection 持有，PacketOut 只保存发送所需的有限历史。

## 4. Stream、流控与调度

### 4.1 Stream

- Stream 由 Connection 创建和查找，Stream ID 按角色分配并校验方向和额度。
- 发送数据进入 Stream ring buffer，直到收到 ACK 才释放；`acquire/commit` 接口可减少应用层复制。
- 接收数据先按 offset 放入有序片段集合，应用读取后再推进消费窗口。
- FIN、RESET_STREAM、STOP_SENDING 和流终态都在 Connection 的控制帧队列中收敛。

### 4.2 流控

- 连接级 `MAX_DATA` 和流级 `MAX_STREAM_DATA` 分别限制接收和发送总量。
- 发送前检查对端额度；额度不足时生成 DataBlocked/StreamDataBlocked 并返回可恢复的写阻塞。
- 应用消费接收数据后推进本端窗口，控制帧通过统一发送控制路径排队。
- 收到更大的额度只前移窗口，不回退已确认的最大值。

### 4.3 调度与拥塞控制

- Connection 内支持 Strict 和 DRR 两种流调度模式，并按 priority 选择可发送流。
- Context 层可使用连接级 WDRR，在多连接同时有数据时分配发送机会。
- BBR 和 CUBIC 共享拥塞控制接口；Pacer 根据拥塞窗口、RTT 和时钟粒度限制发送速率。
- 调度只决定发送机会，不绕过 cwnd、pacing、流控或路径抗放大限制。

## 5. 路径、Keepalive 与 MTU

### 5.1 路径验证

- Connection 维护 active path 和 candidate path。
- 收到来自新 endpoint 的合法包时进入 validating，发送 PathChallenge；只有匹配 PathResponse 后才晋升为 active。
- 每条候选路径独立记录收发字节，并受 `3 * MTU` 抗放大额度限制。
- 候选路径失败不影响当前 active path；数据包响应优先回到触发它的来源 endpoint。

### 5.2 Keepalive

- 连接进入 Connected 后启动空闲计时。
- 收到任意有效入站包会刷新活动时间并清零连续未响应次数。
- 空闲达到间隔后发送 Ping；在超时窗口内没有有效响应则递增探测失败次数。
- 连续失败达到配置上限后以 timeout 原因关闭连接。

### 5.3 MTU 探测

- 握手阶段使用 MTU floor；连接建立后才启动探测。
- 探测按固定梯队推进，梯队结束后在上下界之间二分收敛。
- 探测包独立于业务 PacketOut，使用 Ping + Padding 填充到目标大小。
- `EMSGSIZE`/`WSAEMSGSIZE` 表示本地路径无法承载当前大小：只收窄探测上界，不关闭连接，也不影响其他业务包。
- 探测 ACK、丢失和超时分别回灌 MTU 状态机；黑洞时回退到安全 MTU，冷却后重新验证。

## 6. Crypto、SessionToken 与 0-RTT

- Crypto 模块提供 X25519、HKDF、方向隔离的 AES-GCM 和 SessionToken 编解码。
- 包级 AEAD 使用独立发送/接收 key 和 nonce prefix；解密失败的包不进入连接状态机。
- SessionToken 绑定恢复上下文和有效期，并通过 Context 级短窗口重放表去重。
- 当前明文恢复 0-RTT 和受限的票据流程已接通；加密 early data 只有在早期密钥和重放门控条件满足时才允许。
- 0-RTT 服务端响应保留待确认状态，客户端通过 HandshakeDone 确认实际收到的 Handshake；响应丢失时由重传状态继续发送。

## 7. NAT 探测与 NTRS

### 7.1 NAT 探测

`c/src/nat/` 提供 Context 级异步 NAT 探测。探测结果包含 NAT 类型、主/备用映射、样本数量和 RTT；探测任务可以取消，结果在 Context 内按生命周期缓存。

### 7.2 NTRS 注册

- 一个 Context 对一个 NTRS 维护注册状态、registration token、REGISTER/UNREGISTER 重试副本和保活状态。
- 注册成功后按配置周期发送 Ping；连续三次未收到 PONG 后删除本地注册状态。
- 注册、反注册和地址样本上报都使用幂等 request/update ID，并由统一写事件处理暂不可写。
- Context 销毁不自动反注册；应用应在停止服务前显式调用反注册接口。

### 7.3 Rendezvous 打洞

- 主动连接先生成 `attempt_id` 和本地 CID，再向 NTRS 请求候选计划。
- NTRS 返回的 local/public/预测 endpoint 合并去重；完整 endpoint（IPv6 scope 也包含在比较中）作为去重单位。
- 没有路径反馈时，向候选 endpoint 发送一次 PUNCH 和 Initial；收到合法 PUNCH 后只向其来源 endpoint 重发保留的 Initial。
- NTRS 不转发业务数据，只转发打洞协调控制消息；建立 UTP Connection 后进入普通数据面。
- Rendezvous 失败或关联过期只结束对应的连接尝试，不影响 Context 上其他连接。

## 8. 内存、线程与错误约束

- Context/Connection/Stream 的所有者负责创建和销毁；热路径优先使用池、ring 和侵入式哈希表。
- PacketIn/PacketOut、pending 槽位和 NTRS 控制包使用有界缓存；业务连接数不设固定最大值，资源耗尽通过错误码拒绝新操作。
- Context 的 UDP 读写和协议状态由其事件循环线程处理；回调在约定的事件循环亲和性内执行。
- 公共 API 返回 `utp_status_t`；系统调用错误只在 socket 边界映射一次，不能在下层重复包装。
- 不为不可能状态增加静默 fallback；违反生命周期或线程契约的内部状态使用断言或统一致命错误路径处理。
