# Context、连接与异常处理流程

> 更新时间：2026-09-15
> 本文只描述当前 C11 公共 API 和对应的内部收敛行为；内部状态枚举不是公共接口。

## 1. Context 生命周期

1. 调用方创建并驱动 `struct event_base`，在 `utp_context_options_t` 中提供它和非空 `peer_id`。
2. `utp_context_create()` 创建 Context；Context 借用 event base，不负责销毁它。
   同时借用调用方的 `utp_context_options_t` 直到销毁；连接级选项在每次创建 Connection 时复制，Context 固定选项不得修改。
3. `utp_context_bind()` 创建并绑定一个 UDP socket，可同时指定本地地址、端口和网卡；返回实际端口。
4. 事件循环负责驱动读、统一写事件和协议定时器。
5. `utp_context_destroy()` 停止事件、回收连接/流/池和 socket；它不会隐式调用 NTRS 反注册，也不会触发连接失败回调。

## 2. 主动连接

调用 `utp_context_connect()` 或 `utp_context_connect_0rtt()`：

- `context`、地址、端口、`target_peer_id` 和加密选项必须有效；`target_peer_id` 长度为 1 至 128 字节。
- Context 为本次尝试生成随机 `attempt_id` 和本地 CID，并保留目标 peer-id。
- `timeout_ms` 为单次握手超时，必须大于 0；默认 3000 ms 由 `UTP_CONNECT_OPTIONS_INIT` 提供；`retries=0` 表示不重试。
- Initial 由统一发送路径排队，发送遇到 `UTP_STATUS_WOULD_BLOCK` 时等待 Context 的 writable 事件。
- 收到并验证对端 Handshake 后，Context 发送 HandshakeDone，连接在握手完成条件满足后调用 `on_connected`。

普通直连和通过 NTRS 的 Rendezvous 都经过同一主动连接入口；Rendezvous 只负责候选地址和路径反馈。

### 同步返回与异步回调

参数非法、未 bind、地址解析失败、票据无效、资源不足等前置错误直接由函数返回 `utp_status_t`，不会调用 `utp_on_connect_error_fn`。已经创建尝试后的超时、对端关闭、协议错误或发送终止，才通过 `utp_on_connect_error_fn` 异步报告。

失败回调的 `utp_connect_attempt_info_t` 在回调期间有效，包含目标 endpoint、timeout/retries、加密模式、尝试类型、票据长度和早数据长度。

## 3. 被动连接

收到合法 Initial 后，Context 创建 pending 被动握手并调用 `utp_on_new_connection_fn`。回调返回 false 时拒绝；返回 true 后，调用方通过 `utp_context_accept()` 放行 pending 连接。pending 阶段会按限制缓存必要的后续包并重发 Handshake，完成条件满足后才调用 `on_connected`。

pending 数量受 `pending_incoming_limit` 限制。超过限制或 pending 超时只影响该次尝试，不破坏已建立连接。

## 4. 连接失败和关闭

### 建连阶段

握手期超时、对端发送关闭帧、协议校验失败、CID 冲突或致命发送错误会结束本次 pending/主动尝试，并调用 `utp_on_connect_error_fn`。常见返回状态包括 `UTP_STATUS_TIMEOUT`、`UTP_STATUS_PROTOCOL`、`UTP_STATUS_CLOSED`、`UTP_STATUS_CONNECTION_HANDSHAKE` 和 socket/资源错误。

### 已建立连接

`utp_connection_close()` 请求本地关闭；关闭帧进入统一发送队列，之后连接停止普通业务发送并在有限 PTO 窗口内收敛。对端关闭、保活连续超时、协议错误和本地致命 I/O 错误通过 `utp_on_connection_error_fn` 报告；`UTP_STATUS_OK` 表示对端正常关闭。关闭原因视图只在回调期间有效。

连接关闭后，Context 才从活跃 CID 表移除并回收其 Connection/Stream 对象；应用不得继续使用借用的连接或流指针。

## 5. Stream

`utp_connection_create_stream()` 只允许在已连接 Connection 上创建流，超出对端通告的流数量窗口时返回 `UTP_STATUS_STREAM_LIMITED` 或 `UTP_STATUS_WOULD_BLOCK`。流 ID 由协议角色和方向决定，不应由应用自行计算。

对端创建流时调用 `utp_connection_set_on_incoming_stream()` 设置的回调。读、写、FIN、RESET 和流关闭分别通过 `utp_stream_*` API 及 `utp_stream_set_on_readable/writable/closed()` 回调处理；这些回调均在 Context 事件循环线程同步执行。

## 6. 保活

连接空闲达到 `keepalive_interval` 后发送 Ping；收到任意有效包会刷新活动时间并清零连续失败计数。单次 Ping 在 `keepalive_timeout` 内未得到响应时计数加一，达到 `keepalive_probes` 后连接以 `UTP_STATUS_TIMEOUT` 收敛。保活配置属于新建连接的 Context 默认配置。

## 7. 0-RTT

`utp_context_connect_0rtt()` 在建连调用内将全部 `early_data` 复制到首条双向流的发送缓存；该缓存是早期数据和后续 1-RTT 数据的唯一所有权。首个 0-RTT 包按 MTU 从 offset 0 取前缀，余量在连接进入 `CONNECTED` 后继续按普通 STREAM 发包。早期数据长度不得超过 `stream_send_buffer_capacity`。

0-RTT 包丢失时，发送控制复用同一份 PacketOut，重分配包号并重新执行 AEAD，不重建 Connection 或重新借用调用方数据。服务端 Handshake 的必选 ACK 必须确认任一仍保留的 0-RTT 发送尝试，因而允许确认重传前的旧包号；ACK 才能从发送缓存释放对应前缀。Handshake flight 的退休只回收 PacketOut，不隐式确认流数据。

早期数据可能被重放，应用必须自行保证幂等。服务端先校验票据、有效期、peer 绑定和重放缓存，再由新连接回调决定是否接受。服务端 Handshake 响应和包号会保留到客户端 HandshakeDone 确认或超时清理，应用不需要重新调用 connect 才能触发响应重传。
